# Lab: Reading from a sepcific offset
## Example 1: Start consuming from a specific offset using Spring Boot

### Step 1: Configure Kafka

`application.yml`

```
spring:
    kafka:
        bootstrap-servers: localhost:9092
        consumer:
            group-id: order-service
            auto-offset-reset: earliest
            enable-auto-commit: false
```

`auto-offset-reset: earliest` does not override an existing committed offset. We'll explicitly seek to offset `2` below.

### Step 2: Create the listener

```java
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.apache.kafka.common.TopicPartition;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.listener.ConsumerSeekAware;
import org.springframework.stereotype.Component;

import java.util.Map;

@Component
public class OrderConsumer implements ConsumerSeekAware {

    @Override
    public void onPartitionsAssigned(
            Map<TopicPartition, Long> assignments,
            ConsumerSeekCallback callback) {

        TopicPartition target =
                new TopicPartition("spring-orders", 0);

        if (assignments.containsKey(target)) {
            callback.seek("spring-orders", 0, 2L);
            System.out.println("Seeking to offset 2");
        }
    }

    @KafkaListener(topics = "spring-orders")
    public void consume(ConsumerRecord<String, String> record) {

        System.out.println(
            "Partition: " + record.partition()
            + ", Offset: " + record.offset()
            + ", Key: " + record.key()
            + ", Value: " + record.value()
        );
    }
}
```

### Step 3: Run the application

Assume Partition 0 contains:

```
Offset 0 -> order-101
Offset 1 -> order-102
Offset 2 -> order-103
Offset 3 -> order-104
Offset 4 -> order-105
```

The listener seeks Partition 0 to offset `2` when that partition is assigned.

Expected output begins around:

```
Seeking to offset 2
Partition: 0, Offset: 2, Key: cust-C, Value: order-103
Partition: 0, Offset: 3, Key: cust-A, Value: order-104
Partition: 0, Offset: 4, Key: cust-B, Value: order-105
```

The actual records depend on your topic data and any subsequent assignments or seeks.

Important: This example deliberately seeks to offset `2` whenever Partition 0 is assigned. That means a rebalance can cause the consumer to replay records from offset `2` again. Use this pattern only when you intentionally want that behavior.

## Example 2: Reprocess a specific offset at runtime

Suppose your consumer has been running for several hours and you discover that `order-103` was processed incorrectly. You want to rewind Partition 0 to offset `2` without restarting the application.

You can store the seek callback and invoke it from a controlled service or administrative operation.

For a simple, single-consumer example:

```java
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.listener.ConsumerSeekAware;
import org.springframework.stereotype.Component;

@Component
public class OrderConsumer implements ConsumerSeekAware {

    private volatile ConsumerSeekCallback seekCallback;

    @Override
    public void registerSeekCallback(
            ConsumerSeekCallback callback) {
        this.seekCallback = callback;
    }

    @KafkaListener(topics = "spring-orders")
    public void consume(ConsumerRecord<String, String> record) {
        System.out.println(
            "Offset: " + record.offset()
            + ", Value: " + record.value()
        );
    }

    public void reprocessFromOffset(long offset) {
        ConsumerSeekCallback callback = this.seekCallback;

        if (callback == null) {
            throw new IllegalStateException(
                "Consumer seek callback is not available"
            );
        }

        callback.seek("spring-orders", 0, offset);
    }
}
```

Calling:

```
orderConsumer.reprocessFromOffset(2);
```

requests a seek to offset `2` in Partition 0. Spring Kafka's callback mechanism schedules the seek on the consumer thread.&#x20;

For applications with multiple listener threads, multiple partitions, or multiple consumer groups, you should track the callback for the correct thread and partition rather than using one shared callback.

## Which approach should you use?

Start from a fixed offset

Use `onPartitionsAssigned()` when you intentionally want the consumer to start at a known position.

Reprocess at runtime

Use `ConsumerSeekAware` to seek an already-running consumer back to a specific offset.

Replay a consumer group's history

Stop the group and use `kafka-consumer-groups.sh --reset-offsets` to reset committed offsets.

One final distinction: `seek()` changes the consumer's read position; it does not delete or modify the Kafka record. If you reprocess a record, your application may execute its side effects again, so make those operations idempotent where possible.
